Les fondamentaux

Comprendre le C++ et la compilation

Le C++ est un langage compilé et à typage statique : le compilateur vérifie les types puis produit du code machine pour une plateforme donnée. Il permet de programmer avec des fonctions, des objets et des types génériques. Il sert notamment aux moteurs de jeux, aux logiciels natifs et aux systèmes où le contrôle des ressources est important.

Un fichier HTML affiche ce cours ; il ne compile pas les exemples. Pour les reproduire, enregistrer un programme complet dans main.cpp, puis utiliser un compilateur C++20. Les programmes de ce support sont indépendants : chacun possède son propre main. Il ne faut pas les coller les uns à la suite des autres.

Du fichier source au programme

Le préprocesseur traite notamment les directives #include. Le compilateur analyse le langage, vérifie les types et produit un fichier objet. L’éditeur de liens rassemble les fichiers objets et les bibliothèques. Une erreur de syntaxe bloque la compilation ; une fonction déclarée mais jamais définie peut produire une erreur à l’édition des liens. Une erreur logique peut laisser le programme compiler tout en produisant une réponse incorrecte.

Compiler sur macOS, Windows et Linux

Sur macOS, les outils en ligne de commande Xcode fournissent clang++ ; leur installation initiale se demande avec xcode-select --install. Sur Linux, utiliser GCC ou Clang avec le support C++20. Sur Windows, utiliser soit MSVC et son terminal développeur, soit une chaîne GCC telle que MinGW-w64. VS Code est un éditeur : il ne fournit pas à lui seul un compilateur.

Le standard est choisi explicitement pour éviter de dépendre du réglage par défaut du compilateur. Les avertissements signalent des constructions suspectes ; ils ne prouvent pas l’absence de bugs. Les commandes supposent une chaîne de compilation déjà installée. Le cours lui-même ne nécessite aucune installation.

#include <iostream> donne accès aux déclarations des flux standards. int main() est le point d’entrée du programme. Les accolades délimitent un bloc. std::cout représente la sortie standard et << y insère une valeur. \n produit un saut de ligne. Un point-virgule termine ici l’instruction ; on n’en ajoute pas après chaque accolade, mais une définition de classe se termine par };. Retourner zéro indique un succès au système.

À retenir : compilation, exécution et affichage du cours sont trois opérations différentes. Tous les blocs « programme complet » ci-dessous sont du C++20 ; les blocs de configuration sont identifiés séparément.

Variables, types et expressions

Une variable associe un nom à un objet typé. int représente un entier, double un nombre flottant, bool un booléen et char une unité de caractère. std::string est un type de la bibliothèque standard qui gère une chaîne. La taille de int n’est pas fixée universellement à quatre octets par le langage. sizeof mesure une taille en octets C++, un octet ayant au moins huit bits.

L’initialisation avec {} aide à détecter les conversions réductrices : int n{2.5}; est refusé. Toujours initialiser une variable avant de la lire. auto déduit un type à partir de l’initialisation ; il ne transforme pas C++ en langage à typage dynamique.

7 / 2 vaut 3, car les deux opérandes sont entiers. Convertir le résultat après la division ne restitue pas la partie perdue. Au moins un opérande doit être flottant pour réaliser une division flottante. % calcule le reste d’une division entière. = affecte une valeur ; == compare deux valeurs.

Constantes et précision

const interdit la modification via cette variable après son initialisation. constexpr impose ici une initialisation évaluable à la compilation, par exemple constexpr int seuil{5};. Un const n’est pas toujours une constante de compilation : il peut recevoir une valeur lue pendant l’exécution.

Pour des montants simples, stocker des centimes dans un entier évite les approximations binaires de nombres tels que 0.1. Cela ne règle pas automatiquement les arrondis de taxes ni les dépassements. Un dépassement d’entier signé peut produire un comportement indéfini ; choisir un domaine de valeurs adapté et vérifier les opérations si les données sont externes.

Les fondamentaux

Entrées, conditions et boucles

Le contrôle de flux décide quelles instructions exécuter et combien de fois. Une condition if évalue un booléen ; else traite le cas complémentaire. && et || évaluent leur opérande droit seulement si nécessaire. Cette propriété permet de vérifier une condition préalable avant une opération risquée.

for convient à une répétition dont les étapes sont connues. while répète tant qu’une condition est vraie. Une boucle peut ne jamais s’exécuter ; do ... while exécute son corps au moins une fois. break sort de la boucle la plus proche, tandis que continue passe à l’itération suivante.

Lire une saisie sans masquer les erreurs

Une extraction par >> échoue si le texte n’est pas convertible dans le type demandé. Tester le flux permet d’éviter d’utiliser une saisie invalide. std::getline lit une ligne entière, y compris les espaces. Après une extraction avec >>, un saut de ligne peut rester dans le flux ; std::ws consomme les espaces initiaux avant getline, mais supprime aussi les éventuels espaces voulus en début de nom.

Une interface plus stricte lirait toute la ligne puis vérifierait sa conversion complète : l’extraction de l’entier dans 3abc peut lire 3 et laisser abc pour la suite. Ce programme introduit les flux ; ce n’est pas un validateur exhaustif de formulaire.

Choisir avec switch

switch sélectionne une branche sur une valeur entière ou une énumération. Dans un cas usuel, terminer chaque branche par break évite de poursuivre dans la suivante. Le label default gère les valeurs non prévues. Il n’existe pas de switch direct sur std::string en C++20 : utiliser des conditions ou une table de correspondance.

Les fondamentaux

Fonctions et passage des paramètres

Une fonction regroupe une opération nommée avec un type de retour et des paramètres. Séparer les calculs de l’affichage facilite la réutilisation. La déclaration annonce la signature ; la définition fournit le corps. Le compilateur doit connaître une déclaration avant un appel.

Passer par valeur crée un paramètre distinct : modifier ce paramètre ne modifie pas l’argument. Une référence T& donne accès à l’objet d’origine et permet sa modification. Une référence const T& permet de lire l’objet sans copie par ce paramètre. Pour un petit entier, le passage par valeur est généralement approprié ; pour un conteneur lu sans modification, une référence constante est souvent adaptée.

Une surcharge fournit plusieurs fonctions de même nom avec des listes de paramètres différentes. Le seul type de retour ne permet pas de distinguer deux surcharges. Les arguments par défaut se placent en fin de liste et doivent rester faciles à comprendre.

Piège de durée de vie : ne jamais retourner une référence ou un pointeur vers une variable locale détruite à la sortie de la fonction. Retourner un objet par valeur est souvent le bon choix ; les compilateurs peuvent éliminer des copies et le langage permet les déplacements.

Les fondamentaux

Chaînes, tableaux et conteneurs

La bibliothèque standard fournit des types qui gèrent leur mémoire. std::array<T, N> possède une taille fixe connue à la compilation. std::vector<T> offre une séquence contiguë dont la taille peut évoluer. std::string stocke une séquence de caractères et connaît sa taille.

Les indices commencent à zéro. Pour un conteneur de taille n, le dernier indice valide est n - 1 si n est non nul. operator[] ne vérifie pas les bornes pour vector ; at() les vérifie et lève std::out_of_range en cas d’erreur. Une boucle sur les éléments évite souvent de manipuler les indices.

size() indique le nombre d’éléments, capacity() l’espace actuellement disponible sans nouvelle allocation. reserve() prépare une capacité, mais ne crée pas d’éléments ; resize() change la taille. Un push_back() peut réallouer et invalider tous les pointeurs, références et itérateurs vers les éléments d’un vector.

Les fondamentaux

Références, pointeurs et durée de vie

Une référence est un alias d’objet : elle doit être initialisée et ne peut pas ensuite être reliée à un autre objet. Affecter via une référence affecte l’objet référencé. Un pointeur contient une adresse ; il peut changer de cible ou valoir nullptr pour indiquer l’absence de cible.

&objet obtient une adresse et *pointeur accède à l’objet pointé. Le même symbole a un rôle différent dans une déclaration et dans une expression. Une référence n’est pas un mécanisme de propriété et peut devenir pendante si l’objet disparaît. Un pointeur non nul n’est pas nécessairement valide : sa cible peut déjà avoir été détruite.

const int* empêche de modifier l’entier à travers le pointeur. int* const empêche de changer l’adresse conservée par le pointeur, mais permet de modifier l’entier. Un pointeur brut convient pour observer un objet dont la durée de vie est maîtrisée ; pour posséder une allocation dynamique, préférer un objet de valeur ou un pointeur intelligent.

Comprendre les durées de stockage

Un objet local ordinaire possède généralement une durée de stockage automatique et est détruit à la sortie de son bloc. Un objet statique vit pendant une grande partie de l’exécution. Un objet dynamique vit jusqu’à sa libération. Les mots « pile » et « tas » sont utiles pour comprendre les implémentations courantes, mais le langage définit des durées de stockage sans imposer toute cette organisation physique.

Une variable vector locale peut être détruite automatiquement tout en possédant des éléments stockés dans une allocation dynamique. La portée d’un nom et la durée de vie d’un objet sont donc liées, sans être synonymes. Lire hors limites, déréférencer nullptr ou réutiliser une adresse libérée peut déclencher un comportement indéfini : aucun résultat exploitable n’est garanti.

Objets et C++ moderne

Classes, encapsulation et invariants

Une classe définit un type avec des données et des opérations. Un objet est une instance de ce type. L’encapsulation protège les règles du métier : l’utilisateur de la classe demande une opération, sans modifier directement les détails de représentation. Un invariant est une propriété qui doit rester vraie pour tout objet valide, par exemple « le stock n’est jamais négatif ».

Dans une class, les membres sont privés par défaut. Dans une struct, ils sont publics par défaut ; les deux permettent méthodes, constructeurs et héritage. On emploie souvent struct pour des données simples et class lorsqu’un invariant doit être protégé. Ce sont des conventions, pas deux systèmes de types différents.

Le constructeur initialise l’objet et refuse un état invalide. La liste après : initialise les membres avant l’exécution du corps. Les membres sont initialisés dans leur ordre de déclaration, même si la liste les écrit autrement. std::move sera détaillé au chapitre 20 : ici, il autorise le transfert du contenu du paramètre nom vers le membre.

Le const après une méthode indique qu’elle ne modifie pas les membres ordinaires de l’objet via this. Le getter nom() renvoie une référence constante pour éviter une copie ; cette référence ne doit pas survivre au produit. Ne pas exposer une référence modifiable au stock permet d’empêcher le contournement des contrôles.

Constructeurs et identité

Un constructeur à un seul argument est souvent marqué explicit pour éviter les conversions implicites involontaires. this est le pointeur vers l’objet courant dans une méthode non statique. Une méthode static appartient au type et ne reçoit pas de this. Éviter les setters systématiques : retirer(3) exprime une intention et protège mieux le domaine que setStock(-3).

Constructeurs, délégation et destruction

Un constructeur ne se contente pas de remplir des champs : il établit un objet utilisable. Il porte le même nom que la classe et n’a aucun type de retour, même pas void. On peut fournir plusieurs constructeurs si les paramètres permettent de distinguer des modes de création clairs. Un objet ne reçoit pas un constructeur « à la demande » après sa création : sa construction fait partie du début de sa durée de vie.

La liste d’initialisation construit les membres avant d’entrer dans le corps du constructeur. Une affectation dans ce corps intervient plus tard, sur des membres déjà initialisés. Pour un membre const, une référence ou un objet sans constructeur par défaut, la liste est indispensable. Initialiser directement évite également une construction par défaut suivie d’une affectation.

Un constructeur central pour les règles du domaine

La délégation permet à un constructeur de la classe d’en appeler un autre. Dans l’exemple, la version sans quantité délègue à la version complète. La validation reste ainsi regroupée à un seul endroit.

Le constructeur à un argument est explicit : il empêche notamment la conversion implicite d’un std::string en Produit lors du passage à une fonction. La création directe Produit{"Clavier"} reste autorisée. Définir un constructeur avec paramètres ne donne pas automatiquement un constructeur utilisable sans argument : celui-ci n’est implicitement déclaré que si aucun constructeur n’est déclaré par l’utilisateur.

Si un constructeur lève une exception, l’objet complet n’a pas terminé sa construction et son propre destructeur n’est pas appelé. Les sous-objets déjà construits sont toutefois détruits. C’est une raison essentielle pour placer les ressources dans des membres RAII plutôt que dans des pointeurs bruts dont le nettoyage dépendrait du destructeur de la classe complète.

Observer l’ordre réel des opérations

La base est construite avant les membres du dérivé. Les membres sont construits dans leur ordre de déclaration. À la destruction, le corps du destructeur du dérivé s’exécute avant la destruction de ses membres, puis de ses bases ; les sous-objets suivent l’ordre inverse de construction. Ce programme ne supprime jamais un Service via un pointeur de Base ; il n’exige donc pas un destructeur virtuel pour cette opération inexistante.

Lecture du résultat. Le journal existe déjà au début du corps du constructeur. Il existe encore pendant le corps du destructeur. Après la fermeture du bloc, aucune de ces ressources membres n’existe. Écrire la liste d’initialisation dans l’ordre des déclarations évite de suggérer un ordre différent au lecteur.

Objets et C++ moderne

this, const et conception des méthodes

Une méthode non statique agit sur un objet précis. Dans son corps, this est un pointeur vers cet objet. Écrire this->stock_ n’est généralement pas nécessaire, car le compilateur retrouve le membre ; cela peut aider à lever une ambiguïté de nom. *this désigne l’objet courant.

La constance permet d’exprimer un contrat : observer un objet ne devrait pas le modifier. Une méthode terminée par const peut être appelée sur un objet constant ; une méthode de modification ne le peut pas. Cette distinction agit à la compilation, avant tout lancement du programme.

Surcharger une méthode selon la constance

L’objet modifiable sélectionne la surcharge non constante ; la référence constante sélectionne la surcharge constante. Retourner Inventaire& permet l’enchaînement sans copier le conteneur. La référence renvoyée par stock() devient invalide si son élément disparaît ou si une réallocation l’invalide.

Cet exemple expose une référence modifiable pour expliquer les surcharges : il ne protège pas l’invariant « stock positif ». Pour un domaine réel, une opération contrôlée telle que retirer(position, quantite) est préférable. Un getter qui retourne T& peut donc annuler le bénéfice d’un membre déclaré private.

Ce que const ne garantit pas

Le const d’une méthode n’impose pas une immutabilité profonde de tous les objets accessibles. Si un membre est un pointeur vers un objet modifiable, la méthode peut encore modifier cet objet pointé, selon son type. Un membre déclaré mutable peut aussi être modifié depuis une méthode constante, par exemple pour un cache ; il ne faut pas s’en servir pour contourner une règle métier.

const ne constitue pas une synchronisation entre threads. Une référence constante n’est pas nécessairement un instantané : un autre alias non constant peut encore modifier l’objet. Enfin, retourner une référence constante n’allonge pas automatiquement la durée de vie de l’objet qui contient la donnée. Un résultat par valeur fournit une indépendance plus simple au prix éventuel d’une copie.

Objets et C++ moderne

Membres statiques et séparation des responsabilités

Chaque objet possède ses membres de données ordinaires. Un membre static appartient à la classe plutôt qu’à une instance particulière. Une fonction membre statique n’a pas de pointeur this : elle ne peut pas lire directement le stock d’un produit sans recevoir un produit.

Une constante partagée par toutes les instances et une fonction de validation sans dépendance d’instance sont deux usages possibles. Un compteur global mutable est plus délicat : il impose une politique de copie et de concurrence, et peut devenir une dépendance cachée.

Reservation::estValide(30) s’appelle sans objet. reservation.quantite() lit au contraire la quantité de cette réservation précise. inline autorise ici la définition du membre statique dans l’en-tête sans fournir une définition séparée dans un fichier source. Un membre statique constexpr est implicitement inline depuis C++17 ; l’écriture explicite rend cette propriété visible mais n’est pas nécessaire.

Méthode statique ou fonction libre ?

Une fonction qui n’a besoin d’aucun membre privé peut aussi être une fonction libre placée dans un namespace. Cela évite de créer une classe servant uniquement de sac de fonctions. Une méthode statique reste pertinente lorsque son rôle appartient clairement à l’interface du type.

Un objet de configuration partagé par référence entre plusieurs services n’est pas nécessairement un Singleton. L’unicité d’une instance à un endroit de l’application n’implique pas l’obligation d’un accès global. Conserver la création dans main rend le partage et la durée de vie explicites.

Objets et C++ moderne

Fonctions amies et opérateurs lisibles

L’encapsulation règle quels clients ont accès à la représentation. Une fonction déclarée friend reçoit un accès aux membres privés et protégés de la classe qui l’autorise. Elle n’est pas pour autant une méthode de cette classe. L’amitié est explicite, non réciproque et non transitive ; elle ne se propage pas automatiquement aux classes dérivées.

Une utilisation ciblée est un opérateur qui doit accepter un objet à droite tout en gardant les données privées. Pour un affichage, une méthode publique de lecture suffirait parfois. L’amitié est une décision de couplage à documenter, pas une raison de rendre toute la représentation accessible à tous.

operator<< reçoit le flux par référence et le retourne par référence. Ainsi, std::cout << premier << '\n' enchaîne les insertions dans le même flux sans le copier. La fonction peut lire centimes_ grâce à sa déclaration amie. L’égalité par défaut compare les membres et ne modifie aucun opérande.

Une surcharge ne crée pas un nouvel opérateur ni une nouvelle priorité. Au moins un opérande doit être de type classe ou énumération pour surcharger un opérateur. Certains opérateurs, notamment ::, ne sont pas surchargeables. Donner à + l’effet de débiter un compte ou à == l’effet de modifier un objet rendrait l’interface surprenante même si le compilateur l’acceptait.

Choix pédagogique. Le type présenté n’autorise que les montants non négatifs et reste volontairement réduit. Un modèle comptable pourrait avoir besoin de montants signés, d’une monnaie et d’une politique d’arrondi. Le bon opérateur dépend du contrat du type, pas seulement de sa syntaxe.

Composition, agrégation et héritage

La composition décrit un objet qui possède des sous-objets : une commande possède ses lignes. Le sous-objet membre est construit et détruit avec son propriétaire. Une relation non propriétaire, souvent appelée agrégation dans les modèles, demande une durée de vie externe clairement définie.

L’héritage public exprime une relation de substitution : un objet dérivé doit pouvoir être utilisé selon le contrat du type de base. Il ne sert pas simplement à économiser quelques lignes. Un produit n’est pas un inventaire : l’inventaire contient des produits, ce qui appelle une composition.

Cet exemple emploie des données internes valides pour montrer la composition. Un modèle exposé à des entrées externes vérifierait prix, quantité et dépassements. Les lignes sont stockées par valeur ; aucune allocation manuelle ni suppression explicite n’est nécessaire.

Objets et C++ moderne

Héritage public, protected et accès aux membres

L’héritage public donne au client la possibilité d’utiliser un objet dérivé à travers une référence ou un pointeur de base accessible et non ambigu. Cette conversion structurelle ne suffit pas à garantir une bonne conception : le dérivé doit respecter les attentes attachées au contrat de base.

Les membres private de la base existent dans le sous-objet de base, mais le code du dérivé ne peut pas y accéder directement. Il doit passer par les opérations autorisées. protected rend un membre accessible à la classe et à ses dérivés dans les conditions du langage, sans le rendre public aux clients ordinaires.

Garder les données privées, ouvrir une opération ciblée

Le constructeur du dérivé construit explicitement sa base avec Stock(quantite). Le client peut appeler les membres publics hérités. Il ne peut pas appeler verifierRetrait() ni accéder à quantite_. Une classe dérivée n’obtient donc pas un accès total aux détails de sa base.

Cet exemple utilise une exception pour réemployer la validation, ce qui rend le mécanisme d’accès visible. Pour une consultation fréquente, une requête booléenne explicite dans la base serait plus directe ; les exceptions ne devraient pas devenir le moyen ordinaire de choisir une branche.

class Derive : Base utilise une dérivation privée par défaut ; struct Derive : Base utilise une dérivation publique par défaut. Écrire le mode explicitement facilite la lecture. Polymorphisme et interfaces

Le polymorphisme dynamique permet de choisir une implémentation pendant l’exécution. Une méthode virtual appelée via une référence ou un pointeur de base peut exécuter la redéfinition du type réel. Type statique, type dynamique et slicing

Le type statique est celui connu à la compilation pour une expression. Le type dynamique d’un objet polymorphe décrit le type réel de l’objet le plus dérivé. Une référence de base peut ainsi désigner un objet dérivé sans le transformer.

RAII, propriété, copie et déplacement

RAII associe une ressource à la durée de vie d’un objet. Le constructeur acquiert ou reçoit la ressource ; le destructeur la libère. Cette ressource peut être de la mémoire, un fichier ou un verrou. La destruction automatique des objets locaux libère leurs ressources aussi lorsqu’une exception fait quitter le bloc.

Une allocation avec new et une libération avec delete existent, mais leur usage manuel disperse la responsabilité du nettoyage. Préférer vector, string, les flux de fichiers et les pointeurs intelligents. RAII ne signifie pas « tout mettre sur la pile » : un objet local peut posséder une ressource allouée dynamiquement.

Propriété exclusive avec unique_ptr

unique_ptr ne se copie pas : deux propriétaires exclusifs seraient contradictoires. Son déplacement transfère sa propriété et laisse la source vide. std::move ne déplace rien par lui-même : il convertit une expression pour permettre la sélection d’une opération de déplacement. Un objet standard déplacé reste généralement valide mais dans un état non spécifié, sauf garantie particulière ; unique_ptr garantit ici sa nullité après transfert.

Copie, règle de zéro et partage

Une copie de vector copie ses éléments ; une copie de pointeur brut copie seulement l’adresse. Les types membres déterminent donc une grande partie de la sémantique de copie de la classe. La règle de zéro consiste à confier les ressources à des membres adaptés et à laisser les opérations spéciales générées gérer le reste.

Si une classe gère directement une ressource et définit un destructeur, il faut examiner aussi constructeur de copie, affectation par copie, constructeur de déplacement et affectation par déplacement : c’est la règle des cinq. On peut interdire une opération avec = delete ou demander son comportement généré avec = default.

Une copie cherche généralement à produire une valeur indépendante. Une rvalue recouvre des expressions qui peuvent permettre d’autres choix de surcharge ; les catégories complètes du langage sont plus précises. Même dans une fonction recevant T&&, le nom du paramètre est une expression lvalue : on utilise souvent std::move pour autoriser à son tour le déplacement de ses membres.

Un type propriétaire et non copiable

Le type reste utilisable par déplacement sans promettre une copie qui n’aurait pas de sens. Dans cet exemple, l’état vide est explicitement géré par les méthodes. Il n’est pas nécessaire d’écrire un destructeur qui appelle delete : le membre propriétaire le fait.

Lors d’une réallocation, un vector peut avoir besoin de reconstruire ses éléments. Un switch de création n’est pas automatiquement une erreur : concentré à la frontière d’assemblage, il peut être le choix le plus lisible. Un pattern devient utile quand il réduit un coût concret de modification, de couplage ou de coordination.

Strategy — remplacer un algorithme

Problème. Le calcul des frais de livraison varie selon le mode choisi. Accumuler des conditions dans le service de commande mélange le déroulement de la commande et les politiques tarifaires.

Principe. Le contexte reçoit une stratégie qui expose un contrat commun. Chaque stratégie implémente son calcul. L’algorithme varie sans modifier le contexte.

Commande observe la stratégie : elle ne la détruit pas. Dans main, les stratégies sont créées avant les commandes et restent vivantes pendant les appels. Un autre assemblage pourrait transférer leur propriété avec unique_ptr. Le contrat suppose ici un sous-total valide non négatif.

Quand l’utiliser. Plusieurs politiques interchangeables ont le même rôle : remise, livraison, compression. Limite. Une fonction, une lambda ou un paramètre template suffit souvent pour un algorithme court. Une hiérarchie n’est pas obligatoire pour appliquer l’idée de Strategy.

Factory Method — déléguer la création

Problème. Un traitement commun utilise un exporteur, mais différentes variantes de ce traitement doivent choisir des formats différents.

Principe. Une classe créatrice définit le déroulement du traitement et une méthode de fabrication virtuelle. Ses sous-classes choisissent le produit concret. Ce point distingue Factory Method d’une simple fonction creer(format) contenant un switch.

La méthode generer() reste commune. La création renvoie un propriétaire exclusif et le produit est libéré à la fin de l’appel. Le contrat des méthodes de fabrication impose ici un produit non nul.

Quand l’utiliser. Un framework ou un traitement extensible possède déjà un cycle de vie commun et laisse les sous-classes fournir un composant. Limite. Si seule la création varie, injecter une fonction de fabrication peut éviter une hiérarchie de créateurs.

Abstract Factory — créer une famille cohérente

Problème. Une interface doit construire un bouton et un champ dans un même style. Choisir leurs types séparément expose au mélange de familles incompatibles.

Principe. La fabrique abstraite expose une opération par catégorie de produit. Chaque fabrique concrète construit toute une famille ; le client ne dépend que des contrats abstraits.

La deuxième famille, par exemple sombre, ajouterait BoutonSombre, ChampSombre et FabriqueSombre sans modifier afficher. Une famille suffit dans le code pour montrer le contrat ; ce sont les catégories de produits multiples qui distinguent cette structure d’une simple fabrique.

Quand l’utiliser. Plusieurs composants doivent varier ensemble : interface, pilotes de stockage, composants d’une plateforme. Limite. Ajouter une nouvelle catégorie de produit oblige à modifier le contrat de toutes les fabriques ; le pattern est plus souple pour ajouter des familles que pour ajouter des catégories.

Builder — construire par étapes

Problème. Un rapport possède plusieurs options et un titre obligatoire. Un constructeur avec de nombreux booléens devient peu lisible et les paramètres positionnels se confondent facilement.

Principe. Un constructeur progressif rassemble les choix avec des méthodes nommées, puis produit l’objet final après validation. L’objet produit ne doit pas rester dépendant du Builder.

Chaque méthode retourne *this par référence, ce qui permet l’enchaînement. construire() copie les choix dans un rapport indépendant. La structure résultat reste modifiable dans cet exemple ; un type avec invariant permanent exposerait une interface plus fermée.

Quand l’utiliser. Une construction complexe comporte des étapes ou des options nommées. Limite. Pour trois paramètres simples, une structure de configuration et un constructeur clair peuvent suffire. Un Director, parfois associé à Builder, peut mémoriser des recettes de construction récurrentes ; il n’est pas indispensable ici.

Adapter et Facade — simplifier une intégration

Adapter : traduire un contrat

Problème. Une bibliothèque historique attend un montant en euros, tandis que le domaine utilise des centimes et un contrat Paiement.

Principe. L’adaptateur implémente le contrat attendu et délègue à l’objet existant après traduction des paramètres. Le code client ne connaît pas l’API historique.

La conversion en double précède la division pour éviter une division entière. Dans un système de paiement réel, les montants, erreurs et exigences de précision devraient être traités par contrat ; l’exemple montre uniquement l’adaptation d’interface.

Facade : fournir un point d’entrée simple

Facade regroupe l’accès à plusieurs composants sous une opération de plus haut niveau. Elle ne nécessite pas une incompatibilité d’interface. Elle ne doit pas concentrer toutes les règles métier d’une application.

Quand les utiliser. Adapter raccorde un outil externe à un contrat interne ; Facade réduit le nombre de composants qu’un client doit coordonner. Limite. La façade ci-dessus n’offre pas de transaction : en présence d’échecs réels, il faut définir compensation, atomicité ou reprise. Le pattern seul ne fournit aucune de ces garanties.

Decorator — ajouter des comportements combinables

Problème. Un canal d’envoi peut être journalisé, et demain recevoir d’autres comportements. Multiplier les sous-classes pour toutes les combinaisons ferait croître la hiérarchie.

Principe. Un décorateur implémente la même interface que l’objet enveloppé, le possède ou l’observe, puis ajoute un traitement avant ou après la délégation. Plusieurs décorateurs peuvent être emboîtés.

L’enveloppe et l’objet final présentent tous deux envoyer(). Leur destruction suit la chaîne de unique_ptr. L’ordre des décorateurs compte : chiffrer puis compresser n’a pas le même effet que compresser puis chiffrer.

Quand l’utiliser. Ajouter journalisation, cache ou transformation autour d’un contrat stable. Limite. Les combinaisons peuvent rendre le chemin d’exécution difficile à suivre. Un adaptateur change le contrat exposé ; un décorateur le conserve.

Observer — diffuser un événement

Problème. Une variation de stock intéresse l’écran et un système d’alerte. L’inventaire ne doit pas coder en dur les classes de tous ses consommateurs.

Principe. Le sujet conserve des abonnements et prévient leurs destinataires lorsqu’un événement survient. L’exemple emploie des fonctions de rappel plutôt qu’une hiérarchie d’observateurs.

La copie de la liste crée un instantané : un abonnement supprimé pendant une notification peut encore être appelé durant cette publication, mais plus à la suivante. Cette politique évite l’invalidation des itérateurs lors de modifications réentrantes de la liste ; elle ajoute un coût de copie.

Quand l’utiliser. Notifications locales, rafraîchissement d’interface, événements métier dans un même processus. Limites. Ce code est synchrone et non thread-safe. Une exception d’un rappel interrompt la diffusion. Une lambda capturant une référence vers un objet détruit devient dangereuse : prévoir un désabonnement avant destruction ou un jeton RAII. Observer ne fournit ni file durable ni garantie de livraison réseau.

Command — représenter une action

Problème. Un menu, un bouton et un raccourci doivent déclencher la même opération. On souhaite également conserver un historique d’actions annulables.

Principe. Une commande encapsule l’action, son destinataire et les données nécessaires. L’invocateur manipule le contrat de commande sans connaître le métier du destinataire.

L’objet stock vit plus longtemps que la commande qui le référence. L’état executee_ empêche une annulation avant exécution ou une double exécution accidentelle. Les quantités utilisées sont petites et le stock n’est modifié par aucun autre acteur.

Quand l’utiliser. Historique d’éditeur, planification locale, actions de menus. Limite. Une annulation n’est pas toujours l’opération arithmétique inverse : paiement, envoi réseau et actions concurrentes nécessitent une compensation ou un état sauvegardé. Le stockage de références en mémoire ne permet pas de sérialiser automatiquement une commande dans une file distante.

State — faire varier le comportement d’un objet

Problème. Une commande brouillon accepte le paiement ; une commande déjà payée refuse un second paiement. Des conditions réparties entre toutes les opérations rendent les transitions difficiles à suivre.

Principe. Le contexte délègue à un objet représentant l’état courant. Les états définissent les comportements autorisés et les transitions possibles. Contrairement à Strategy, le changement représente ici l’évolution du cycle de vie métier.

L’état propose son successeur sans se détruire pendant l’exécution de sa propre méthode. Le contexte remplace l’état seulement après le retour. Si la création du successeur échoue, l’ancien état reste en place. Dans une application de paiement, l’événement « payé » devrait refléter une confirmation du prestataire : le code illustre le cycle de vie, sans paiement réel.

Quand l’utiliser. Workflow avec de nombreux comportements dépendant de l’état. Limite. Pour deux états et une seule opération, une énumération et un switch centralisé peuvent rester plus lisibles. Le pattern devient intéressant lorsque plusieurs opérations évoluent ensemble selon l’état.

Composite — traiter un arbre uniformément

Problème. Un lot contient des articles et d’autres lots. Le calcul du prix doit fonctionner de la même façon sur un élément simple et sur un groupe.

Principe. Une interface commune représente la feuille et le composite. Le composite possède ses enfants et délègue récursivement l’opération à chacun.

La propriété exclusive forme un arbre : chaque enfant appartient à un seul parent. Pour partager des éléments ou créer un graphe, il faudrait définir d’autres règles de propriété et empêcher les cycles dans les parcours.

Quand l’utiliser. Arborescences de fichiers, scènes graphiques, menus ou nomenclatures. Limite. Toutes les opérations ne sont pas pertinentes pour les feuilles : conserver ajouter() dans Lot évite de faire semblant qu’un article peut recevoir des enfants. Une profondeur non maîtrisée peut aussi épuiser la pile d’appels.

Singleton — connaître le mécanisme et ses coûts

Problème. On veut un point d’accès unique à une instance donnée dans le programme. Singleton combine le contrôle de construction et l’accès global à cette instance.

Principe. Le constructeur est privé, la copie interdite, et une méthode statique retourne une instance locale statique. Depuis C++11, l’initialisation d’une telle variable locale statique est synchronisée entre threads.

La synchronisation concerne l’initialisation, pas l’ensemble des futures opérations sur des données mutables. Une instance locale statique est détruite à l’arrêt normal du programme ; des dépendances entre objets statiques peuvent compliquer leur ordre de destruction. Le pattern ne crée pas automatiquement une instance unique partagée entre processus.

Quand l’utiliser. Un besoin d’unicité et d’accès global est réellement imposé et ses conséquences sont maîtrisées. Limites. Dépendances cachées, état global et remplacement difficile dans les tests. Pour une configuration applicative, une instance créée dans main et injectée explicitement est souvent plus facile à contrôler. Connaître Singleton permet aussi de reconnaître les cas où il vaut mieux s’en passer.

Types métier, énumérations et opérateurs

Un type métier rend une intention plus explicite qu’un entier anonyme. Une énumération fortement typée enum class rassemble des valeurs nommées sans les convertir implicitement en entier. Deux énumérations différentes restent deux types différents, même si leurs valeurs sous-jacentes se ressemblent.

La surcharge d’opérateurs permet d’utiliser une syntaxe familière pour un type défini par l’utilisateur. Elle doit conserver une signification attendue : == compare, + combine sans modifier ses opérandes dans les usages usuels. Elle ne change ni la priorité ni le nombre d’opérandes des opérateurs.

L’égalité générée avec = default compare les membres ; cette forme demande C++20. La fonction libelle() traite chaque valeur nommée du statut. Le retour de secours couvre notamment une valeur produite par une conversion explicite hors des valeurs nommées. L’absence de default permet à certains avertissements de signaler un nouveau cas oublié.

Un struct ReferenceProduit n’est pas automatiquement une référence mémoire : son nom appartient au vocabulaire métier. Ce petit type évite de mélanger accidentellement un identifiant de produit et un identifiant de client si chacun possède son propre type. Pour garantir un identifiant strictement positif, un constructeur validant et un membre privé seraient nécessaires.

Exemple d’ensemble — un inventaire et ses frontières

Cet exemple réunit les notions dans un petit service : un dépôt fournit les données, une politique décide de l’alerte et le service orchestre l’affichage. Il n’ajoute pas tous les patterns à la fois : seuls les points de variation utiles sont représentés.

Le dépôt mémoire possède ses produits par valeur. Le service observe ses dépendances. La recherche renvoie une copie optionnelle du produit : ce choix simple évite de renvoyer une référence dont le client devrait maîtriser la durée de vie. Pour un catalogue très volumineux, les copies et les accès mériteraient une autre politique.

Lire les responsabilités

Produit est un type de données. DepotProduits est un contrat d’accès ; il n’impose pas de base SQL. DepotMemoire implémente ce contrat avec un vector. PolitiqueAlerte joue le rôle de Strategy. ConsultationStock dépend des abstractions, et main choisit les implémentations.

Remplacer la politique n’exige pas de modifier le dépôt. Remplacer le dépôt n’exige pas de modifier le calcul d’alerte. En revanche, changer la structure de Produit peut affecter les deux : les dépendances ne disparaissent pas, elles deviennent explicites.

Limites assumées du modèle

Ce programme utilise des données internes déjà valides, une recherche linéaire et aucune concurrence. Il n’offre ni persistance, ni contrainte d’unicité des identifiants, ni réservation de stock. Une application réelle doit définir ces contrats avant de multiplier les abstractions. Séparer un présentateur de ConsultationStock deviendrait pertinent si l’affichage variait entre console, API et interface graphique.

Quelques habitudes durables

Préférer des valeurs simples et des durées de vie explicites. Passer les dépendances au lieu de les chercher dans un état global. Protéger les invariants au moment des changements.
